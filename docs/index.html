An AI copilot for grant intake

It reads PDF/DOCX/TXT applications, classifies eight fields against closed taxonomies, shows verified evidence and a confidence score for every field, forces a human decision, and produces a canonical record plus a Salesforce payload — while never touching Salesforce.

Scope

What it is, what it isn't

The goal is not to replace Salesforce or to integrate with production yet. It is to prove, end to end, that a real application can be parsed, classified with traceable evidence, and turned into a record ready to ship — with a person validating every decision that matters.

✅ It is

  • An extraction + classification pipeline with structured outputs validated against Pydantic.
  • An explicit, replaceable confidence heuristic — never presented as a calibrated probability.
  • A review layer that blocks any Medium/Low field from shipping without an explicit decision.
  • A SalesforceAdapter that builds and displays the payload — and never sends it.
  • Taxonomies, thresholds and field mapping fully configurable in YAML.

🚫 It is not (yet)

  • A real Salesforce integration (OAuth, Composite API, MuleSoft, Apex).
  • OCR for scanned PDFs — it stops and reports "OCR required" instead of guessing.
  • Fine-tuning, embeddings, vector DB or RAG.
  • Multi-tenant, SSO, or an enterprise deployment.
  • A replacement for human judgement: confidence never decides anything on its own.
Architecture

Decoupled by design

The AI, the classification and the human validation layer don't know Salesforce exists. Only SalesforceAdapter, driven by salesforce_mapping.yaml, knows that format — and in this phase it only builds the payload, never sends it.

Methodology

Eight fields, closed taxonomies

FieldTypeCardinalityTaxonomy
organization_nameExtraction1—
amount_requestedExtraction (normalized amount)1—
project_summarySynthesis (≤ 600 chars)1—
grant_typeClassification1grant_types.yaml
primary_strategyClassification1strategies.yaml
issuesMulti-label classification0..nissues.yaml
geographyMulti-label classification0..ngeographies.yaml
target_populationMulti-label classification0..npopulations.yaml

Issue areas cover housing, economic justice, health, immigration, environment, gender-based violence, LGBTQ+ rights and reproductive rights, with matching target populations — all editable in YAML, no code change required.

One call, dynamic schema

All eight fields are resolved in a single structured call per document. The output schema is built at runtime with Literal[...] from the current YAML files, so the model can only pick values that exist in the taxonomy — free text is structurally impossible.

1Ingest + validate 2Build schema from taxonomies 3One structured LLM call 4Verify evidence 5Score confidence 6Human review

Evidence is verified by code, not by the model

Every quote is normalized (case, whitespace, smart quotes) and searched literally in the real page text; if there is no exact hit, it falls back to fuzzy matching (difflib, ratio ≥ 0.85). The page number stored is the one found by the code — the page the model claims is discarded. A hallucinated quote is flagged unverified and drags the confidence down; the demo ships with a sample that deliberately triggers this.

Each piece of evidence is also tagged explicit (the concept appears verbatim) or inferred (it was deduced), and the reviewer sees which is which.

Confidence

A heuristic, not a probability

Read this first → An LLM's self-reported confidence is not calibrated. The UI always labels the score "(heuristic)" and every run records the method as heuristic-v1, so it can be replaced by a calibrated model later without rewriting history.
confidence = 0.50·evidence_quality + 0.15·evidence_count + 0.20·coherence + 0.15·self_confidence

Hard caps: a classified field with no verified evidence cannot exceed 0.60; an Other value cannot either; a null value or empty list drops to 0 and the field moves to Needs review.

Levels only prioritize review — they never decide

High ≥ 90% Medium ≥ 70% Low < 70%

Human-in-the-loop rules

  1. 1
    Every prediction shows its value, confidence, evidence and review state (pending / approved / edited / rejected / needs review).
  2. 2
    "Approve all High-confidence fields" touches only High fields. Medium and Low always require an individual decision.
  3. 3
    Bulk approvals are flagged bulk=True in the audit trail, and the headline metric is reported both with and without them — so the acceptance rate can't be quietly inflated.
  4. 4
    "Finalize review" stays disabled while any field is still pending or needs review.
  5. 5
    The original prediction and the final human value are both stored. A prediction is never overwritten.
Data flow

What goes out, what gets stored

To the LLM (one call per document, only to the provider you pick): the prompt with the current taxonomies injected, the extracted text with [[PAGE n]] markers, and the dynamic response schema. The filename and metadata are never sent, and the original file is never stored.

TableContents
documentsid (sha256 of the bytes), filename, type, page count
document_pagesthe document text itself, per page or section
runsprovider, model, prompt_version, taxonomy_version, status, reviewer
model_outputsthe raw model output, untouched
predictionsvalue, confidence, level and evidence per field
review_decisionsthe audit trail: one row per human decision, append-only, never overwritten
approved_recordsapproved canonical JSON and the Salesforce payload

Document content and model output never reach the logs. Every run records model_name, model_version, prompt_version, taxonomy_version and app_version — the basis for measuring accuracy and calibrating confidence once enough reviews accumulate.

In action

The full loop

Upload → extraction with highlighted evidence → field-by-field review → approved record → Salesforce payload → pilot metrics. Running locally on the Fake provider, so no LLM is called at all.

Salesforce readiness

Ready to connect, not connected

config/salesforce_mapping.yaml declares, per field, the target object, the Salesforce field and an optional value_map. SalesforceAdapter.to_salesforce(...) assembles the payload grouped by object — without importing any Salesforce SDK or opening a connection.

What a real integration would add

  1. 1
    Authentication — a Connected App with OAuth 2.0 JWT Bearer flow (server to server), certificate held in a vault.
  2. 2
    Transactional writes — Composite API (allOrNone: true) or sObject Tree to create Account + Grant_Request__c in one call.
  3. 3
    No duplicate accounts — upsert by External ID instead of always inserting.
  4. 4
    Picklist validation against describe() before sending, compared with the live taxonomy.
  5. 5
    Partial failures and retries — backoff on 5xx and API limits, idempotency keyed on run_id.
  6. 6
    Sandbox before production, with the same custom fields and a permissions checklist.
What doesn't change → ingestion, pipeline, LLM layer, confidence, review, models and audit trail. Only salesforce_adapter.py is touched, plus a new client that ships the already-generated payload.
